# 2026-11-15 - Шаг 9: окно настроек, срок хранения, полное удаление данных

## Задача

Закрыть обещания ТЗ, которых не было в коде: ФТ-7.2 (окно настроек: исключения приложений и каталогов, список «не записывать никогда», срок хранения, полное удаление данных), ФТ-2.3 (исключение из настроек действует без перезапуска), ФТ-3.1 (порог простоя настраиваемый), ФТ-6.1 (хосты плана восстановления собираются из фактов сессии), §4.6 (срок хранения настраивается, полное удаление стирает базу вместе с -wal/-shm).

## Что сделано

### Настройки и применение на лету

- `Core/Domain/Settings.cs`: `AppSettings` (исключения приложений и каталогов, правила, срок хранения, порог простоя) + `NeverRecordRule(Kind, Value)` с видами из спеки §4.3 (имя приложения, хост URL, подстрока пути) + ограничения диапазонов.
- `SettingsService` (ключи `privacy.apps`, `privacy.dirs`, `privacy.never`, `retention.days`, `session.idle_minutes`; значения - JSON). Битый JSON или отсутствие ключа - умолчания, без исключений.
- `ExclusionSet` переписан: состояние - неизменяемый снимок за volatile-ссылкой, `Apply(AppSettings)` собирает новый снимок (дефолты внутри всегда: менеджеры паролей, `%APPDATA%\Microsoft\Credentials`, `.ssh`, `.gnupg`, `Packages`). `IsNeverRecorded` реализован по трём видам правил. Чтение из конвейера, запись из UI - гонок нет.
- `SessionSupervisor` берёт порог простоя через `IIdleThresholdProvider` на каждом тике - смена настройки действует сразу.

### Срок хранения и удаление

- `IRepository.DeleteSessionsOlderThanAsync` (EF, `ExecuteDeleteAsync`): дочерние таблицы раньше родительских (FK `NO ACTION`), висячие сессии не трогаются, 0 дней - бессрочное хранение.
- `RetentionService`: прогон при старте, раз в 6 часов и сразу после сохранения настроек (подписка на `Changed`).
- `DataWipeService`: `SqliteConnection.ClearAllPools()`, удаление `continuum.db` + `-wal` + `-shm`, схема создаётся миграциями заново, настройки перечитываются (умолчания).
- `MaintenanceCoordinator`: останавливает супервизор и снапшоттер, закрывает сессию, стирает, пересоздаёт, открывает новую сессию, запускает таймеры - приложение продолжает работать без перезапуска. В демо-режиме кнопка удаления недоступна.

### Окно настроек

- `SettingsViewModel` (MVVM, без зависимостей от окна): списки с добавлением/удалением без дублей, поля срока хранения и порога, сохранение, удаление данных через шов `IUserConfirmation`, событие `DataWiped`.
- `SettingsWindow.xaml`: три секции списков, секция хранения, кнопки «Сохранить», «Удалить все данные», «Закрыть», строка статуса. Code-behind - только окно.
- Вход: кнопка «Настройки» в главном окне и пункт «Настройки...» в меню трея (окно одно, повторный вызов активирует открытое).

### Хосты плана восстановления (ФТ-6.1)

- `RestorePlanComposer`: приложения сессии по событиям с `ApplicationId` → имя процесса из exe-пути; открытые файлы последнего снапшота с `Line` → `code -r -g "путь:строка"` (проверка наличия `code` через `IApplicationResolver`; без него - файлы остаются обычными `OpenFile`).
- `RestoreService.BuildPlanAsync` получил набор файлов, покрытых хостами: такие файлы шагами `OpenFile` не дублируются.

## Нашлось и исправлено по ходу

- **DI-ошибка**: `MaintenanceCoordinator` просил конкретный `Snapshots.Snapshotter`, а контейнер отдавал только `ISnapshotter` - открытие окна настроек роняло процесс с `InvalidOperationException: Unable to resolve service`. Исправлено: конкретный снапшоттер зарегистрирован синглтоном, интерфейс делегирует ему (как сделано с адаптером VS Code).
- Ранние «нет окна» в проверке оказались артефактом UI Automation в этой среде: перечисление окон падает с COM `E_UNEXPECTED`, а не проблемой приложения. Проверка переведена на трассу по коду + `IsLoaded/IsVisible` окна.
- Первые два теста нового набора падали по неверной постановке: ожидание «повторный прогон удалит 1» (на деле фоновая реакция уже удалила) и стирание настроек в тесте, где сервис настроек смотрел в фейковый репозиторий вместо реальной базы. Исправлены ожидания и стенд.

# Спецификация: Privacy Pipeline

- Статус: **нормативный документ**. Расхождение между этим файлом и реализацией — дефект реализации.
- Область: конвейер обработки наблюдаемых данных до записи в БД; исключения; санитизация секретов; retention; удаление данных.
- Смежные документы: [`readme.md`](../../readme.md) (скоуп, схема БД, разделы «Чего Continuum не делает» и «Данные и приватность»), [`data-sources.md`](data-sources.md) (что именно доступно).

---

## 1. Принцип

> **Capture context ≠ capture everything.**

Continuum видит чувствительное: URL, пути файлов, командные строки, названия проектов. Поэтому «захват всего → SQLite» запрещён. Обязательная модель:

```text
Observable → Filter → Sanitize → Persist
```

Ни одна запись не попадает в БД в обход конвейера. Это проверяется юнит-тестом, а не соглашением.

Конвейер существует **до первой записи в БД**, а не появляется вместе с `SettingsWindow`: сначала пишем защищённо, потом добавляем UI для правки правил.

## 2. Контракты

Объявлены в `Continuum.Core`, реализованы в `Continuum.App/Infrastructure/Privacy`.

```csharp
// Единица наблюдения до обработки
public sealed record Observable(
    ObservableKind Kind,        // WindowTitle | FilePath | Url | CommandLine | Cwd
    string? Value,
    int? ProcessId,
    string? ApplicationName,
    string? ApplicationExePath,
    DateTimeOffset Timestamp,
    string? ProjectRootPath);

public interface IPrivacyFilter
{
    // false = отбросить целиком, не записывать ничего
    bool Allow(Observable o);
}

public interface ISanitizer
{
    // маскирует чувствительные подстроки, возвращает безопасное значение
    string Sanitize(string value, ObservableKind kind);
}

public interface IExclusionSet
{
    bool IsApplicationExcluded(string applicationName, string? exePath);
    bool IsDirectoryExcluded(string path);
    bool IsNeverRecorded(Observable o);
}
```

Порядок применения в `ContextService`:

```text
1. IExclusionSet.IsApplicationExcluded   → отбросить
2. IExclusionSet.IsDirectoryExcluded     → отбросить (для FilePath, Cwd)
3. IExclusionSet.IsNeverRecorded         → отбросить
4. IPrivacyFilter.Allow                  → отбросить
5. ISanitizer.Sanitize                   → заменить значение
6. Persist
```

Отбрасывание на шагах 1–4 — полное: ни события, ни поля в снапшоте, ни строки в Timeline. Не «сохранить, но скрыть в UI».

## 3. Разрешения коллекторов

Каждый коллектор объявляет, какие виды `Observable` он имеет право выдавать. Коллектор не может выдать вид, которого нет в его разрешениях; нарушение — дефект, ловится тестом.

| Коллектор | Разрешённые виды |
| --- | --- |
| `ProcessCollector` | (служебные, без значений: pid, exe) |
| `WindowCollector` | `WindowTitle` |
| `FileActivityCollector` | `FilePath` |
| `RecentDocumentsCollector` | `FilePath` |
| `GitClient` | `FilePath` (dirty-файлы) |
| `TerminalCollector` | `Cwd`, `CommandLine` |
| `ChromeTitleCollector` | `WindowTitle` |
| `ChromeUrlCollector` | `Url` |
| `VSCodeAdapter` | `FilePath` |

`CommandLine` и `Url` — два самых чувствительных вида. Они проходят санитизацию в обязательном порядке, даже если правила исключений пусты.

## 4. Исключения

### 4.1 Исключённые приложения

Не наблюдать приложение целиком: ни окон, ни заголовков, ни URL, ни процессов-детей.

Сравнение — по нормализованному имени процесса (без учёта регистра, без расширения) и по пути exe. Путь важнее имени: два разных продукта могут называться одинаково.

По умолчанию в списке (предзаполняется при первом запуске, пользователь может снять):

```text
Менеджеры паролей:     1password, keepass, bitwarden, enpass, dashlane, lastpass,
                       nordpass, stickypasswords, keeper
Банковские клиенты:    (по имени exe — заполняется пользователем)
Приватные мессенджеры: (по выбору пользователя)
Continuum:             continuum   ← собственное окно всегда исключено
```

Собственное приложение исключается безусловно и неудаляемо из списка: иначе Continuum записывал бы собственные настройки и собственные заголовки.

### 4.2 Исключённые директории

Не наблюдать пути внутри каталога. Сравнение — по нормализованному префиксу пути (регистронезависимо, с разрешением `..`, с учётом точек монтирования и subst).

По умолчанию исключены всегда, неудаляемо:

```text
%APPDATA%\Microsoft\Credentials
%LOCALAPPDATA%\Microsoft\Credentials
%USERPROFILE%\.ssh
%USERPROFILE%\.gnupg
%APPDATA%\..\Local\Packages\*   (контейнеры приложений UWP)
```

По умолчанию исключены, снимаемо:

```text
%USERPROFILE%\Documents (частично — по выбору)
Любые сетевые пути \\*
Любые съёмные носители (по выбору)
```

Пользовательские исключения хранятся в `settings` как список путей.

### 4.3 «Не записывать никогда»

Отдельный список правил поверх исключений. Правила трех видов:

```text
BY_APP_NAME    значение совпадает с именем приложения
BY_HOST        хост URL совпадает с доменом или его суффиксом
BY_PATH_SUBSTR подстрока в пути (например "\bank\", "\private\")
```

`BY_HOST` применяется **только когда URL реально получен** (`url_available = 1`). Если доступен лишь title вкладки, правило по хосту применить невозможно — это ограничение фиксируется явно (раздел 8).

## 5. Санитизация секретов

`ISanitizer` применяется к `CommandLine` и `Url` всегда, независимо от настроек.

### 5.1 Командные строки

Маскируется значение, имя параметра сохраняется:

```text
--password=SuperSecret123        →  --password=***
-p "SuperSecret123"              →  -p ***
--token ghp_xxxxxxxxxxxx         →  --token ***
AWS_SECRET_ACCESS_KEY=abc...     →  AWS_SECRET_ACCESS_KEY=***
ghp_[A-Za-z0-9]{36}              →  ***            (GitHub PAT по форме)
sk-[A-Za-z0-9]{20,}              →  ***            (API-ключ по форме)
xox[baprs]-[A-Za-z0-9-]+         →  ***            (Slack-токен по форме)
AKIA[0-9A-Z]{16}                 →  ***            (AWS access key по форме)
-----BEGIN [A-Z ]*PRIVATE KEY-----[\s\S]*?-----END → ***
```

Правила:

- маскирование **жадное к значению, осторожное к форме**: при сомнении маскировать;
- длина исходного значения не сохраняется (не `***123`, не `***(12)`) — иначе раскрывается энтропия;
- маскирование применяется **до** любых проверок «содержит ли строка исключённый путь», чтобы секрет не попал в логи сравнения;
- список паттернов — данные (конфиг), а не хардкод: пользователь может добавить свой.

### 5.2 URL

Из URL удаляются компоненты, способные нести секрет или PII:

```text
user:password@host      →  host            (credentials в authority)
?token=..., ?key=..., ?sig=..., ?auth=..., ?code=..., ?password=..., ?secret=...
                        →  параметр сохраняется как <name>=***
#fragment               →  удаляется целиком (SPA-роуты могут содержать данные сессии)
```

Сохраняются: схема, хост, путь, имена query-параметров. Значения параметров — по правилу выше.

### 5.3 Пути файлов

Пути **не маскируются** — они и есть основная ценность контекста. Защищаются только исключениями директорий (раздел 4.2).

Исключение: если имя файла совпадает с паттерном секретного артефакта, событие отбрасывается целиком:

```text
*.pem  *.key  *.pfx  *.p12  id_rsa  id_ed25519  *.kdbx  .env  .npmrc  .netrc  credentials.json
```

Отбрасывается **событие**, а не только имя: сам факт наличия `.env` в проекте полезной информации не несёт, а раскрывать структуру секретов не нужно.

## 6. Retention

Настраиваемый срок хранения. По умолчанию **90 дней**.

```text
retention_days                = 90
retention_max_db_mb           = 500        (второй порог, срабатывает любой из них)
retention_cleanup_on_startup  = true
retention_cleanup_interval_h  = 24
```

Очистка удаляет каскадно, в транзакции, в порядке зависимостей:

```text
restore_steps → restore_plans → open_files / git_state / terminals / browser_tabs
→ snapshots → file_activity → events → sessions (не активная)
→ осиротевшие applications / projects (last_seen < порога)
```

Активная сессия (`ended_at IS NULL`) не удаляется никогда.

После массовой очистки выполняется `PRAGMA wal_checkpoint(TRUNCATE)`, чтобы файл действительно уменьшился. `VACUUM` — только по явной команде пользователя в `SettingsWindow` (дорого, блокирует БД).

## 7. Удаление данных

Три уровня, все доступны из `SettingsWindow`:

| Уровень | Действие |
| --- | --- |
| **Удалить период** | Очистка по диапазону дат (те же каскады, что retention) |
| **Удалить проект** | Все данные, связанные с `project_id`, включая события, файлы, снапшоты |
| **Удалить всё** | Закрытие БД, удаление `continuum.db`, `continuum.db-wal`, `continuum.db-shm` и каталога `%LOCALAPPDATA%\Continuum\` |

Требования:

- «Удалить всё» работает при запущенном приложении: сначала корректное закрытие соединения, потом удаление файлов. `-wal` и `-shm` удаляются обязательно, иначе часть данных переживёт удаление;
- подтверждение с явным текстом о необратимости;
- после удаления приложение перезапускает инициализацию БД (пустое состояние, `FirstRunDialog`);
- удаление не оставляет резервных копий и не синхронизируется никуда: сетевых вызовов у Continuum нет.

## 8. Известные ограничения

Фиксируются честно. Каждое из них — место, где UI обязан показывать «недоступно» вместо пустоты или выдуманного значения.

### 8.1 Приватные окна браузера не детектируются

Ни заголовок окна, ни процесс, ни командная строка не позволяют уверенно отличить профиль incognito/guest от обычного. Обещание «не записывать приватные окна» **не может быть выполнено надёжно**.

Формулировка для UI и для защиты:

> Continuum применяет исключения по приложениям и доменам, когда источник данных доступен. Приватные окна браузера не определяются как отдельный режим; для гарантии не-записи исключите приложение целиком.

### 8.2 Точный URL вкладки Chrome — не гарантирован

В заголовке окна Chrome находится title страницы, не URL. URL доступен только через UI Automation и только когда браузер построил accessibility-дерево. Следствия:

- правила `BY_HOST` применяются лишь при `url_available = 1`;
- при `url_available = 0` в БД пишется title, а в UI отображается «URL недоступен»;
- точный список всех вкладок всех окон — **non-goal** MVP.

Подробности и таблица способов — в [`data-sources.md`](data-sources.md), раздел «Chrome».

### 8.3 Командные строки дочерних процессов

Continuum читает `CommandLine` процессов своего пользователя. Если секрет передаётся через переменные окружения родительского процесса (а не через аргументы), он в наблюдаемые данные не попадает. Обратное тоже верно: паттерны санитизации покрывают не все формы секретов, поэтому исключения приложений (4.1) — первичный механизм защиты, а санитизация — второй.

### 8.4 Момент применения правил

Исключения применяются **в момент наблюдения**. Данные, записанные до добавления исключения, задним числом не пересматриваются — для этого есть «Удалить период» / «Удалить всё» (раздел 7). Поведение документируется в UI, чтобы не создавать ложного ожидания.

## 9. Обязательные тесты

Конвейер — та часть системы, где молчаливый дефект означает утечку. Минимальный набор:

```text
PrivacyFilter
  · исключённое приложение → все виды Observable отброшены
  · исключённая директория → FilePath внутри отброшен, снаружи — пропущен
  · сетевой путь \\server\share при включённом правиле → отброшен
  · собственное приложение (continuum) → отброшено, правило неудаляемо

Sanitizer
  · каждый паттерн из 5.1 маскируется, имя параметра сохраняется
  · credentials в authority URL удаляются
  · query-параметры token/key/sig/auth/code/password/secret маскируются
  · fragment удаляется
  · длина секрета не раскрывается в выходе
  · пути *.pem / *.key / .env / id_rsa → событие отброшено целиком

Retention
  · удаление каскадно, сирот не остаётся
  · активная сессия не удаляется
  · после очистки размер файла уменьшился (wal_checkpoint)

Deletion
  · «Удалить всё» стирает db, -wal, -shm
  · после удаления приложение инициализирует пустую БД

Конвейер целиком
  · ни одна запись в БД не минует Filter и Sanitize (интеграционный тест)
```

## 10. Хранение настроек приватности

Настройки хранятся в таблице `settings` (ключ/значение, JSON для списков) в той же БД.

Последствие, которое надо понимать и озвучивать: **правила исключений лежат рядом с данными, которые они защищают.** Удаление БД удаляет и правила (при следующем запуске восстанавливаются значения по умолчанию). Это приемлемо для локального single-user инструмента и сознательно выбрано ради принципа «одна папка = всё состояние».

Отдельного пароля или шифрования БД в MVP нет. Обоснование: данные принадлежат одному пользователю, лежат в его профиле и защищены ACL Windows; шифрование ключом, хранящимся рядом с БД, безопасности не добавляет, а усложняет восстановление. Шифрование — кандидат после MVP, вместе с подписью RestorePlan.

# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## на курсовой проект «Continuum - локальная система сохранения и восстановления рабочего контекста»

по дисциплине «Разработка программных модулей»

Репозиторий проекта: <https://github.com/norwenkenji/Continuum>

---

## 1. Введение

### 1.1. Наименование программы

Continuum (Чтение: «континуум») - локальная система сохранения, анализа и восстановления рабочего контекста пользователя для ОС Windows.

### 1.2. Краткая характеристика области применения

Во время работы пользователь одновременно держит открытыми редактор кода, терминал, браузер с документацией и другие приложения. После перерыва, перезагрузки или аварийного завершения штатные средства ОС отвечают только на вопрос «что было открыто», но не отвечают на вопрос «над чем шла работа и на каком этапе она остановлена».

Continuum решает эту задачу: система непрерывно собирает объективные факты о работе (процессы, окна, файлы, состояние git-репозитория), строит из них хронологию сессии и точки состояния (снапшоты), отвечает на вопрос «где я остановился?» детерминированным алгоритмом и формирует план восстановления рабочего окружения.

---

## 2. Основания для разработки

Основание для разработки - задание на курсовой проект по дисциплине «Разработка программных модулей»: разработать десктопное приложение на C# + WPF с применением архитектурного паттерна MVVM и подключением базы данных.

---

## 3. Назначение разработки

### 3.1. Функциональное назначение

Программа предназначена для:

1. автоматической фиксации рабочего контекста пользователя: активные приложения и окна, файловая активность по проектам, состояние git-репозиториев (ветка, последний коммит, незакоммиченные файлы), системные события (сон/пробуждение, завершение сеанса);
2. ведения append-only хронологии рабочей сессии;
3. снятия снапшотов состояния контекста по таймеру и на границах сессии;
4. формирования ответа «где я остановился?» по детерминированной таблице истинности без применения нейросетевых моделей;
5. построения и выполнения плана восстановления рабочего окружения (RestorePlan) с результатом по каждому шагу (success/partial/failed) и режимом dry-run.

### 3.2. Эксплуатационное назначение

Программа эксплуатируется на персональном компьютере под управлением Windows 10/11 под обычной (непривилегированной) учётной записью пользователя. Программа не требует прав администратора, установки служб и драйверов, изменения системных настроек и доступа к сети.

## 4. Требования к программе

### 4.1. Требования к функциональным характеристикам

#### 4.1.1. Состав функций

1. **Сбор наблюдений (коллекторы):**
   - мониторинг активного окна и запуска/завершения процессов (WinAPI, без прав администратора);
   - определение проекта по пути файла или рабочей директории через git root;
   - наблюдение за git-репозиториями проектов (только читающие команды, таймауты, работа при отсутствии git без ошибок);
   - наблюдение за файловой активностью (FileSystemWatcher на корнях проектов с исключениями служебных каталогов; журнал «Recent» Windows);
   - регистрация коммитов и переключений веток как событий хронологии.
2. **Privacy-конвейер:** каждое наблюдение до записи в базу данных проходит фильтрацию по исключениям (приложения, каталоги, «не записывать никогда») и санитизацию (маскирование секретов в командных строках и URL). Ни одна запись не минует конвейер.
3. **Сессии:** автоматическое определение границ рабочей сессии (запуск, простой по GetLastInputInfo с настраиваемым порогом, завершение сеанса Windows, выход пользователя), восстановление после аварийного завершения (висячая сессия закрывается временем последнего события).
4. **Снапшоты:** периодическая и событийная фиксация состояния (по каждому проекту: ветка, HEAD, список незакоммиченных файлов).
5. **Движок «Где я остановился?»:** детерминированная таблица истинности по фактам (последний проект, последний файл, состояние git) с тремя исходами: «работа, возможно, не завершена», «работа завершена», «статус неясен».
6. **План восстановления (RestorePlan):** упорядоченные шаги восстановления (приложение - окно - файлы/URL), режим dry-run, независимость результата каждого шага.
7. **Пользовательский интерфейс:** главное окно со сводкой последней сессии, хронология, ответ «где я остановился?», окно настроек (исключения, срок хранения, полное удаление данных), значок в области уведомлений (трей).
8. **Демонстрационный режим:** запуск с параметром `--demo` заполняет отдельную базу данных синтетической реалистичной сессией для показа полного цикла на любом компьютере.

#### 4.1.2. Требования к организации входных и выходных данных

Входные данные - только локальные источники: WinAPI (процессы, окна, время бездействия), файловая система (ярлыки Recent, файлы проектов), вывод git.exe (только читающие команды), базы данных VS Code (state.vscdb, User/History). Выходные данные - база данных SQLite и пользовательский интерфейс WPF. Сетевых вызовов программа не выполняет.

#### 4.1.3. Требования к надёжности

- отсутствие любого внешнего инструмента (git, VS Code, Chrome) не является ошибкой: соответствующий источник помечается недоступным, остальные функции продолжают работу;
- сбой одного наблюдения или одного шага восстановления не прерывает работу программы;
- при недоступности источника данных интерфейс обязан показывать «недоступно», а не пустое или выдуманное значение;
- события хронологии не редактируются и не удаляются задним числом (кроме явной команды полного удаления данных).

#### 4.1.4. Требования к ресурсам

| Метрика | Цель |
| --- | --- |
| Средняя загрузка CPU | < 1-2% одного ядра |
| Потребление RAM | < 150 МБ |
| Рост базы данных | < ~10 МБ/сутки |

События записываются только при изменении состояния, а не по таймеру; опросы источников имеют ограничения по частоте.

### 4.2. Требования к информационной и программной совместимости

- Язык и платформа: C#, .NET 10 (`net10.0` - переносимое ядро без WinAPI и WPF; `net10.0-windows` - оболочка).
- UI: WPF с применением архитектурного паттерна MVVM (модели представления без зависимости от представления, покрываются юнит-тестами).
- База данных: SQLite, встраиваемая, через Microsoft.Data.Sqlite; миграции схемы - через PRAGMA user_version.
- Архитектурное правило: ядро (`Continuum.Core`) не зависит от оболочки; инфраструктура и адаптеры реализуют интерфейсы, объявленные в ядре (инверсия зависимостей); правило проверяется архитектурным тестом.
- Хранилище данных пользователя: `%LOCALAPPDATA%\Continuum\`; удаление папки полностью удаляет данные.
- Код покрыт юнит-тестами (xunit); таблица истинности движка «где я остановился?» покрыта тестами на всех ветках.

### 4.3. Требования к защите информации

- данные не покидают компьютер пользователя (local-first, сетевых вызовов нет);
- privacy-конвейер применяется до первой записи в базу;
- поддерживаются исключения приложений и каталогов, список «не записывать никогда», маскирование секретов, настраиваемый срок хранения, полное удаление данных (включая служебные файлы SQLite -wal/-shm);
- программа не делает скриншотов, не перехватывает клавиатуру, не читает содержимое файлов и страниц (только пути, заголовки и метаданные), не изменяет репозитории пользователя.

### 4.4. Условия эксплуатации

Обычная учётная запись Windows без административных прав. Развёртывание - копированием папки с программой (portable, zero-setup): при первом запуске программа сама создаёт хранилище.

## 6. Стадии и этапы разработки

| Этап | Содержание | Результат |
| --- | --- | --- |
| 0 | Разделение на Core/App, DI, пути, часы | Ядро собирается без `-windows` |
| 1 | Домен, SQLite, миграции, privacy-конвейер | БД создаётся при первом запуске; ни одна запись не минует конвейер |
| 2 | Коллектор процессов/окон, трей | Смена окна - ровно одно событие |
| 3 | Проекты, git, file_activity | Проект по пути; без git - available=0 без исключений |
| 4 | Сессии, снапшоты | Crash-recovery; снапшот при завершении сеанса |
| 5 | Движок «Где я остановился?» | Тесты на всех ветках таблицы истинности |
| 6 | RestorePlan, MVVM-инфраструктура | Dry-run ничего не запускает; падение шага не отменяет остальные |
| 7 | Адаптер VS Code | Открытые файлы читаются из фактов |
| 8 | Демо-режим, юнит-тесты | Полный цикл на машине без VS Code и git |
| 9 | Окно настроек | Исключение действует без перезапуска |
| 10 | Адаптеры Chrome и терминала | Честная деградация при недоступности UIA |

Этапы 0-5 на момент сдачи ТЗ завершены и подтверждены тестами и живыми прогонами (см. журнал `docs/ai-log/`).

## 7. Порядок контроля и приёмки

1. Сборка решения без ошибок и предупреждений (`dotnet build`).
2. Все юнит-тесты проходят (`dotnet test`); таблица истинности движка «где я остановился?» покрыта на всех ветках.
3. Живой прогон: запись событий в БД, событие коммита, снапшот при выходе, восстановление после принудительного завершения процесса.
4. Демонстрационный сценарий из раздела 20 `plan.md`: создание демо-проекта, работа, завершение сессии, показ хронологии и «где я остановился?», восстановление сессии.
5. Проверка бюджета ресурсов через Диспетчер задач.
